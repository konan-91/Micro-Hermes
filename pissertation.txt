2. Related Work

2.1 Traditional CPU and Network Scheduling

The problem of distributing work across CPU cores has a long history in
operating systems research. Classical CPU schedulers, such as the
Completely Fair Scheduler (CFS) in Linux, aim to divide processing time
equitably among threads based on runtime metrics (Molnar, 2007). These
schedulers operate at the process level and are well-studied; however,
they are not designed to account for the nature of individual network
connections or the imbalance that can arise when some requests are
significantly heavier than others.

Network scheduling has similarly been studied in the context of packet
queuing and traffic shaping, with disciplines like weighted fair queuing
(WFQ) designed to prevent any one flow from monopolising bandwidth
(Demers et al., 1989). While these approaches are foundational, they
operate at the traffic level rather than the application level and do
not address the worker-level fairness problem that arises inside a
single server process.

While historical OS scheduling shares the core goal of distributing
uneven workloads fairly, it operates in a completely different
environment. Older research provides a helpful conceptual framework, but
it does not offer a direct technical solution for routing tasks inside a
single server application.

2.2 Linux Connection Scheduling Mechanisms

Modern Linux provides two primary mechanisms for distributing incoming
connections across multiple workers: epoll_exclusive and SO_REUSEPORT.

epoll_exclusive, introduced in Linux 4.5, allows multiple threads to
wait on the same epoll file descriptor such that only one thread is
woken per event, avoiding thundering herd issues (Linux man-pages,
2023a). However, it offers no insight into worker busyness. The kernel
selects a worker without knowing whether it is already processing a
heavy or long-lived request.

SO_REUSEPORT allows multiple sockets to bind to the same port, with the
kernel distributing incoming connections across them using a hash of the
source address and port (Linux man-pages, 2023b). This is statistically
fair across many connections but is equally blind to application-level
worker state. A worker that happens to receive several slow or expensive
connections will become overloaded while others sit idle.

Both mechanisms are widely used in high-performance servers (nginx,
envoy, etc.) precisely because of their simplicity and low overhead. The
limitation they share, blindness to userspace worker status, is the
central problem Micro-Hermes addresses.

2.3 eBPF and Kernel Programmability

eBPF (extended Berkeley Packet Filter) allows user-defined programs to
be safely injected into the Linux kernel at designated hook points,
verified by a kernel-side verifier before execution (eBPF.io, 2024).
Originally designed for packet filtering, eBPF has expanded into a
general-purpose kernel extension mechanism used for tracing, security
enforcement, and networking.

In the networking context, eBPF programs can be attached at various
layers of the kernel stack. The XDP (eXpress Data Path) hook sits at the
network driver layer, allowing programs to process raw packets before
they enter the kernel networking stack which makes it suitable for
ultra-low-latency packet forwarding. The SO_ATTACH_REUSEPORT_EBPF socket
option, by contrast, hooks into the socket selection layer and allows an
eBPF program to override the kernel's default reuseport hashing logic,
deciding which socket receives each new connection. This is the hook
used by Hermes, and by Micro-Hermes.

The eBPF verifier ensures that injected programs cannot crash the kernel
or loop infinitely, making this a safe mechanism for extending kernel
behaviour without kernel module development. Toolchains such as Aya (a
Rust-native eBPF library) allow eBPF programs to be written and loaded
from Rust, which is the approach taken in this project.

2.4 Layer 4 eBPF Load Balancing

A significant body of recent work applies eBPF at Layer 4 (the transport
layer) for load balancing across clusters of servers. These systems are
designed for high-throughput packet forwarding in data centre
environments.

Meta's Katran is a widely deployed example: it uses eBPF and XDP to
perform consistent-hash-based load balancing across backend servers at
line rate, handling tens of millions of packets per second per core
(Manekar & Narayanan, 2018). Cilium similarly leverages eBPF to replace
kube-proxy in Kubernetes environments, providing cluster-wide load
balancing and network policy enforcement without the overhead of
iptables (Cilium Authors, 2024).

Recent academic work has continued in this direction. arkLB proposes an
adaptive, rack-aware Layer 4 load balancer using eBPF and XDP, targeting
data centre topologies to reduce cross-rack traffic (will get citation
later!). HEELS and the CRAB load balancer represent further efforts to
improve consistency and efficiency of packet-level forwarding using
kernel bypass techniques (here also, lv4 balancers so do not need to
explain in depth).

These systems are all highly relevant as prior art, but they address a
fundamentally different problem from Micro-Hermes. Because they operate
at Layer 4, on raw packets before the kernel's networking stack
processes them, they have no visibility into application-layer
information such as HTTP headers, TLS session state, or per-worker
processing loads. They cannot determine whether a particular worker
process is idle or overwhelmed. Their goal is infrastructure-scale
traffic distribution, not intra-server worker fairness.

2.5 Layer 7 and Application-Aware Load Balancing

Layer 7 load balancers operate at the application layer and can make
routing decisions based on application-level information such as request
type, headers, or session affinity. Software load balancers such as
HAProxy and Nginx perform Layer 7 load balancing in userspace, typically
acting as reverse proxies that accept all connections and forward them
to backends (HAProxy Technologies, 2024). While flexible and
feature-rich, these systems introduce additional latency from the proxy
hop and are not designed for the intra-server, kernel-level dispatching
problem.

The paper most directly relevant to this project is Hermes (Pan et al.,
2025), an industry system from Alibaba Cloud that tackles the worker
overload problem at Layer 7 using an eBPF-based approach. Hermes
introduces a Worker Status Table (WST) maintained in shared memory, into
which application workers continuously write their real-time load
metrics (pending events, accumulated connections, and timestamps). An
eBPF hook at the SO_ATTACH_REUSEPORT_EBPF layer reads this table at
connection arrival time and dispatches each new connection to the
least-loaded available worker, preventing overload before it occurs. The
results reported are striking and resulted in a 99.8% reduction in daily
worker hangs and an 18.9% reduction in infrastructure unit cost in
production at Alibaba Cloud.

Hermes is closed-source, however, and operates at hyperscale within a
proprietary infrastructure stack. Micro-Hermes aims to reproduce the
core architecture in an open-source, single-node Rust implementation,
validating the approach at smaller scale and making it accessible to
organisations without Alibaba-scale infrastructure.

XLB (Peking University, 2026) is a related recent system that removes
the sidecar proxy from microservice communication by placing load
balancing logic directly in eBPF at the kernel level. Rather than
requiring service A to route via a sidecar proxy to reach service B, XLB
intercepts inter-service messages in the kernel and consults an internal
load map to determine which instance of B should receive the request.
Like Hermes, XLB demonstrates that kernel-level, status-aware dispatch
can outperform proxy-based approaches. Unlike Hermes (and Micro-Hermes),
XLB targets inter-server microservice communication rather than
intra-server worker dispatch, making it a complementary rather than
directly competing approach.

2.6 Positioning Micro-Hermes

The related work above reveals a clear gap: while Layer 4 eBPF load
balancing is mature and well-studied, application-aware intra-server
dispatching (preventing individual worker processes from becoming
overloaded while others sit idle) remains largely the domain of
proprietary, closed-source industry systems like Hermes. Open-source,
reproducible implementations that validate and democratise this approach
are absent from the literature.

Micro-Hermes addresses this gap by providing an open-source, single-node
implementation of the Hermes architecture in Rust. It targets the same
SO_ATTACH_REUSEPORT_EBPF hook, implements the Worker Status Table in
shared memory, and benchmarks the resulting system against standard
Linux mechanisms. In doing so it both validates the original paper's
claims at smaller scale and provides a foundation that smaller
organisations can build on.

4. Design

4.1 Two-Phase Approach and System Architecture Overview

Micro-Hermes is developed in two phases. Phase 1, the subject of this
dissertation, is a complete userspace simulation of Hermes's three-stage
feedback loop: every architectural element of the original system (the
Worker Status Table, the per-worker scheduler, the connection
dispatcher, and the shared-memory communication between them) is
implemented faithfully, while the two elements that require a Linux
kernel (the eBPF dispatch program and real sockets) are replaced by
userspace stand-ins with equivalent interfaces. Phase 2, left to future
work, replaces those stand-ins with a real eBPF program attached via
SO_ATTACH_REUSEPORT_EBPF. The component boundaries of the Phase 1
implementation are drawn deliberately along the kernel/userspace line so
that this transition replaces components rather than restructuring the
system.

The simulation reproduces Hermes's division of labour with real
operating-system processes. A parent process stands in for the kernel:
it generates synthetic connection arrivals at a configurable rate,
computes a hash standing in for the kernel's 4-tuple hash of each
connection, runs the dispatch mechanism under test, and places each
connection into the chosen worker's accept queue. Four forked child
processes stand in for the load balancer's workers, each running the
instrumented run-to-completion event loop from the Hermes paper:
timestamp the loop entry, collect a batch of events (an epoll_wait
analogue over the accept queue, with the paper's 5 ms timeout),
process each event, maintain the status metrics, and, at the end of
every iteration, run the scheduling pass. All cross-process state (the
Worker Status Table, the candidate bitmap, and the accept queues) lives
in a single region of shared anonymous memory mapped before forking.

Crucially, the feedback loop is closed: a worker's load consists
exclusively of the connections the dispatcher assigned to it, and the
dispatcher's decisions are driven by the bitmap the workers' schedulers
publish. Scheduling decisions therefore directly shape the measured
load distribution, which is the property the evaluation exercises.

4.2 Worker Status Table

The WST follows the layout described by Pan et al. (2025): one slot per
worker holding the three status metrics, each stored as an individually
atomic 64-bit integer. The metrics are the timestamp of the most recent
event-loop entry (used for hang detection), the count of pending events
(events delivered by epoll_wait but not yet handled, a proxy for
instantaneous processing load), and the accumulated count of open
connections (a guard against future overload from synchronised bursts
on long-lived connections). Each slot is padded to a 64-byte cache line
to prevent false sharing between workers on adjacent cores.

The concurrency design is preserved exactly: the table is partitioned
by writer, with each worker updating only its own slot, and the
scheduler reads the entire table without locks. Reads may race with
updates from other workers; as in the original system this is accepted
by design, since per-field atomicity prevents torn values and a
marginally stale metric does not meaningfully change a scheduling
decision.

4.3 Kernel Connection Dispatcher

The dispatcher implements Hermes's Algorithm 2. For each new connection
it reads the candidate bitmap from M_Sel, counts the set bits, and, if
more than one candidate survives, scales the connection's hash into the
candidate count using the Linux kernel's reciprocal_scale function (a
multiply-and-shift mapping, reimplemented exactly) and selects the Nth
set bit of the bitmap. If one or zero candidates survive, it falls back
to plain reuseport hashing across all workers, matching the paper's
fallback rule: dispatching every connection that arrives between
scheduler updates to a single "best" worker would itself overload it.

Although Phase 1 executes this logic in the parent process rather than
in the kernel, it is written under eBPF's constraints (no heap
allocation, statically bounded loops) so that the Phase 2 port to an
eBPF program is mechanical. M_Sel itself is modelled as a single shared
atomic 64-bit integer, mirroring the atomic read/write guarantee that a
single-element BPF_MAP_TYPE_ARRAY provides in the real system; only the
internals of this component change in Phase 2.

4.4 Userspace Scheduler

Every worker runs Hermes's Algorithm 1 at the end of each event-loop
iteration: there is no dedicated scheduler process, exactly as in the
original design. The scheduler snapshots the WST and applies three
cascading filters in the paper's fixed priority order. The time filter
removes workers whose last loop entry is older than a hang threshold
(200 ms in this implementation; the paper leaves the constant
implementation-defined). The connection-count filter and the
pending-event filter each remove workers whose metric exceeds the
candidate average plus an offset theta, which prevents the candidate
set from collapsing when workers are near-uniformly loaded. Following
the paper's empirical finding that theta/avg = 0.5 is optimal, theta is
computed as half the candidate average, with a small floor so the
filter remains permissive at cold start. The surviving set is encoded
as a bitmap and written to M_Sel with a single atomic store.

Because the scheduler runs once per loop iteration and epoll_wait is
bounded by a 5 ms timeout, every worker is guaranteed to re-enter its
loop, and therefore to refresh its timestamp and re-run the scheduler,
at least once every 5 ms even with no traffic at all, keeping both
hang detection and the candidate set live under idle conditions.

4.5 Alternative Scheduling Algorithms

Two baseline dispatch mechanisms are implemented for comparison,
modelling the standard Linux mechanisms described in Section 2.2. Under
the reuseport baseline, the dispatcher applies reciprocal_scale to the
connection hash across all workers unconditionally, reproducing
SO_REUSEPORT's stateless behaviour: no awareness of worker state, and
no scheduler runs at all.

The epoll-exclusive baseline models the kernel's actual wakeup
mechanism rather than a caricature of it. In the kernel, the listen
socket's wait queue is ordered by epoll_ctl registration, and each
registration is inserted at the head of the list, so the queue order
is static: the last-registered worker sits permanently at the head. An
incoming connection wakes the first idle worker found by traversing
from the head. The simulation reproduces this with generator-visible
state: registration order is fork order, so the highest-numbered
worker is the head of the wait queue; a worker counts as idle when its
accept queue is empty and it has no pending events; and when no worker
is idle the connection goes to the shortest backlog, approximating the
shared accept queue that the next free worker would drain. All
workers, baseline and Hermes alike, run the paper's 5 ms epoll_wait
timeout; why this is safe for the baseline is discussed in
Section 5.4.

5. Implementation

5.1 Rust Toolchain and eBPF Integration

Phase 1 is implemented in stable Rust with a single dependency (libc,
for mmap, fork and waitpid), approximately 1,600 lines across nine
modules, with unit tests covering the scheduler's filters, the
dispatcher's bit manipulation, and the shared-memory queue. No eBPF
toolchain is required yet, but the codebase is structured for the
Phase 2 integration with Aya: the dispatcher is verifier-compatible as
written, the M_Sel wrapper exposes the same store/load interface as an
Aya array-map handle, and the WST and scheduler carry over unchanged
since they remain in userspace in the real system.

5.2 Shared Memory Communication

All cross-process state lives in one structure mapped with
mmap(MAP_SHARED | MAP_ANONYMOUS) before forking, so the parent and all
workers share the same physical pages without any IPC machinery, and
atomic operations on the shared pages are well-defined across the
process boundary. Alongside the WST and M_Sel, the region contains one
single-producer single-consumer ring buffer per worker, standing in
for the kernel's per-socket accept queue. Because each ring has
exactly one producer (the generator) and one consumer (the owning
worker), acquire/release ordering on the head and tail indices is
sufficient and the design remains lock-free throughout, mirroring the
WST's partitioned-writer principle. A full ring rejects the
connection, modelling accept-queue overflow.

5.3 Simulating the Kernel Dispatch Path

The parent process paces connection arrivals against absolute
deadlines at the workload's target connections-per-second, so sleep
jitter does not accumulate as rate drift. Each connection carries a
synthetic 4-tuple hash (a counter mixed with a multiplicative constant,
optionally perturbed by a per-trial seed), a sampled per-connection
processing cost, and a lifetime after which the receiving worker closes
it. Workers simulate L7 processing by sleeping for the connection's
cost; processing expense is thus a property of the connection rather
than the worker, matching the paper's characterisation of variable L7
cost (TLS handshakes, compression, protocol translation).

5.4 Engineering Challenges

Three issues encountered during implementation are worth recording.
First, metrics collection across fork(): an early design accumulated
benchmark records in a mutex-protected vector placed in the shared
region, which is unsound; a vector's heap allocation is not in the
shared mapping, and standard-library mutexes are undefined across
processes on some platforms (on macOS the underlying os_unfair_lock
aborts with EINVAL). Each worker instead buffers records privately and
writes its own file shard, which the parent merges after waitpid,
applying the WST's single-writer partitioning idea to the benchmarking
plumbing itself.

Second, a subtle fidelity artefact in the epoll-exclusive baseline.
An early version modelled the wait-queue head dynamically, as the
worker with the most recent loop-entry timestamp, and gave idle
baseline workers a periodic housekeeping timer. Because the workers
are forked simultaneously, their timers were phase-locked: each expiry
re-stamped a different worker in lock-step, rotating the concentration
target about once a second and producing per-worker totals that were
artificially near-balanced, masking the very pathology the baseline
exists to demonstrate. The fix was to model what the kernel actually
does: the wait-queue order is set at epoll_ctl registration time and
is static, with the last-registered worker permanently at the head.
With a static queue order, idle wakeups no longer reshuffle priority,
so every policy can safely share the paper's 5 ms epoll_wait timer,
and the baseline exhibits the persistent concentration the real
mechanism shows.

Third, batch sizing: real L7 events cost microseconds, but the
simulation's per-event sleeps cost milliseconds, so a realistic
epoll_wait batch limit would stretch a single loop iteration past the
hang-detection threshold and starve the scheduler of fresh status
data. The batch limit is therefore kept small (4 events), preserving
the paper's property that scheduler frequency scales with load.

6. Evaluation

6.1 Evaluation Framework and Methodology

The evaluation reproduces the four traffic regimes used by Pan et al.
(2025), characterised by connections-per-second (CPS) and
per-connection processing cost: Case 1, high CPS with low cost (a
stress or traffic-spike scenario); Case 2, high CPS with high cost
(compression-heavy traffic, configured here as a sustained overload at
roughly 112% of aggregate worker capacity, with a 400 ms stall
injected into one worker); Case 3, low CPS with low cost but
long-lived connections that never close within the run (the
finance/chat pattern, and the most common case in Alibaba's
production); and Case 4, low CPS with high cost (TLS- and regex-heavy
web services at roughly 75% utilisation). A fifth scenario, beyond the
paper's four, repeats Case 3's accumulation of long-lived connections
and then fires a follow-up request on every open connection
simultaneously, providing direct evidence for the cost of connection
concentration (Section 6.2, Case 5).

Each of the three dispatch policies is run against each case three
times, with a per-trial seed varying the (reproducible) sequence of
connection hashes and sampled processing costs. Two record streams are
collected: one row per completed connection (arrival, dequeue and
completion timestamps, so that latency includes both queueing delay
and service time), and one row per worker event-loop iteration (a WST
snapshot plus, for Micro-Hermes, the scheduler's per-stage survivor
counts and bitmap). Percentiles are computed within each trial and
then aggregated across trials. Load balance is measured as the
standard deviation of per-worker connection counts, the metric the
Hermes paper uses for its production comparison. The full pipeline,
from benchmark execution to every figure and table referenced below,
is reproducible from a single annotated Jupyter notebook in the
project repository.

6.2 Benchmarks: Micro-Hermes vs reuseport vs epoll_exclusive

Case 1 (high CPS, low cost). When requests are cheap and the system is
far below capacity, all three policies deliver essentially the same
latency: every policy completes a typical connection in 1.3 ms. The
mechanisms differ sharply in how fairly they spread the work. Across
the 1,200 connections of a run, Micro-Hermes distributes most evenly
(a standard deviation of 14 connections between workers, against 29
for reuseport), while the epoll-exclusive model sends every single
connection to the wait-queue head worker (standard deviation 520):
because each request is processed faster than the next one arrives,
the head worker is always idle again in time to be woken next, and the
other three workers never receive anything. Micro-Hermes's tail is
marginally higher than the baselines' (99th percentile 1.9 ms against
1.4 ms) because, in one trial, a handful of connections (about 0.6%)
briefly queued behind busy candidates — a direct cost of restricting
dispatch to a candidate subset, and consistent with the paper's own
ranking for this regime, which places plain reuseport marginally ahead
of Hermes when load is trivially light.

Case 2 (high CPS, high cost, with an injected hang). This case pushes
the offered load slightly past what the four workers can process, so
queues grow throughout the run and latency is dominated by waiting.
Here awareness of worker status pays off directly: Micro-Hermes
achieves a mean latency of 570 ms against reuseport's 784 ms (27%
lower), and a 99th percentile of 1,579 ms against 2,037 ms.
The gap has a simple cause: reuseport's hash does not know that a
worker is busy or stalled, so it keeps sending roughly a quarter of
all new connections to the stalled worker for the full duration of
the stall, while Micro-Hermes routes around it. The epoll-exclusive
model posts the lowest latency of all (mean 414 ms); Section 6.5
explains why this is a boundary of the simulation rather than a
property of the real mechanism.

Case 3 (low CPS, long-lived connections). This case reproduces the
paper's headline production result. Because connections never close
within the run, every dispatch decision is permanent: mistakes
accumulate instead of washing out, and the balance of open connections
at the end of the run exposes each mechanism's character. The
epoll-exclusive model ends with a standard deviation of 104
connections — the head worker holds all 240 connections of the run
while the other three hold none — against 15 for Micro-Hermes and 14
for reuseport. This is the same ordering the paper reports from
production (standard deviations of 3,200, 50 and 20 for exclusive,
reuseport and Hermes respectively). Micro-Hermes matches rather than
beats reuseport here; Section 6.5 discusses why parity is the faithful
expectation in this synthetic setting.

Case 4 (low CPS, high cost). With expensive requests at moderate
utilisation (about 75%), the danger is queueing a new connection
behind a slow one on an already-busy worker. Micro-Hermes's
99th-percentile latency of 442 ms is less than half of reuseport's
975 ms, precisely because it avoids doing that; reuseport, hashing
blindly, cannot. The epoll-exclusive model again leads (295 ms), with
Micro-Hermes tracking it as the paper predicts: Hermes's closed-loop
status detection reacts with a small lag where exclusive's wakeup of
an idle worker is immediate.

Case 5 (synchronized burst on long-lived connections). Cases 1 to 4
measure the latency of new connections, which cannot show why
concentration is dangerous: a worker hoarding idle connections pays no
visible penalty while they stay idle. Case 5 makes the danger
measurable. It repeats Case 3's accumulation — by 2.5 seconds each
policy has dispatched roughly 150 long-lived connections — and then
every open connection fires one 5 ms follow-up request at the same
instant, modelling the synchronized bursts (a market opening for
finance traffic, a mass push notification for chat) that the WST's
connection-count metric exists to guard against. Because a request on
an established connection can only be processed by the worker that
owns it, the burst is processed exactly as unevenly as the connections
were dispatched. Under the epoll-exclusive model the head worker owns
all of the connections and must work through the entire backlog alone:
the median follow-up waits 405 ms and the 99th percentile 801 ms.
Micro-Hermes and reuseport, having spread the same connections across
all four workers, complete the same burst with a median of 107 ms and
a 99th percentile of roughly 250 ms — the four-fold parallelism the
machine actually has. This is the measured form of the trade-off the
raw latency numbers of Cases 2 and 4 conceal: the epoll-exclusive
model's fast dispatch coexists with a standing liability that comes
due the moment its hoarded connections wake up.

Across all five cases Micro-Hermes never collapses: where it is not
the best policy it trails the best by a fraction of a millisecond
(Case 1) or a bounded margin (Cases 2 and 4), whereas each baseline
fails badly in at least one regime — epoll-exclusive on balance in
Cases 1 and 3 and on burst latency in Case 5, reuseport on latency in
Cases 2 and 4. This adaptability, rather than outright victory in any
single regime, is the core property claimed for the Hermes
architecture, and the simulation reproduces it.

6.3 Worker Hang Prevention Results

Case 2 injects a 400 ms stall into one worker mid-run, modelling the
edge-triggered starvation hangs that motivated Hermes. The recorded
scheduler decisions show the mechanism operating as designed. In every
trial the stalled worker is removed from the candidate bitmap in a
sustained exclusion window of 300-400 ms bracketing the stall. The
worker typically drops out of candidacy almost immediately, because it
stalls while still holding a batch of unprocessed events and the load
filters already exclude it on that basis; the time filter then
guarantees the exclusion from 200 ms into the stall (the configured
hang threshold), once the worker's loop-entry timestamp has gone
stale. It is readmitted shortly after the stall ends, when it
re-enters its loop and re-stamps the WST. Notably, exclusion is
enacted by the other workers' schedulers, since the stalled worker
cannot run its own; this confirms the value of embedding the scheduler
in every worker rather than in a dedicated process. During the same
window the reuseport baseline continues to assign roughly a quarter of
new connections to the stalled worker: the failure mode that motivated
Hermes's timestamp-based hang detection, observed directly.

6.4 Scheduler Filter Behaviour

The per-stage survivor counts recorded at every scheduling pass show
the cascading filter behaving as the paper describes. Under light load
(Cases 1 and 3) the filters barely prune: on average 3.7 to 3.8 of the
four workers survive all three stages. Under load the candidate set
contracts, most sharply in the overloaded Case 2, where the mean
surviving set falls to 2.6 of 4 workers after the third filter, with
the event-count filter doing the most work. Case 2 is also the only
case where the time filter prunes appreciably (a mean of 3.5 survivors
after stage one): beyond the injected stall itself, a worker that
spends several hundred milliseconds inside a single loop iteration
processing a batch of slow events looks, from the WST's point of view,
exactly like a hung worker — and is treated as one, which is arguably
correct, since it cannot accept new work promptly either way. Overall
this matches the paper's observation that the fraction of workers
passing the coarse filter decreases as load increases, while theta's
margin prevents collapse to a single candidate, which would forfeit
the kernel-side fine-grained selection and trigger the fallback path.

6.5 Discussion

Two results deviate from the paper's rankings, and both are boundaries
of a userspace simulation rather than defects of the architecture;
they are recorded here as honest limitations of Phase 1.

First, the epoll-exclusive model wins on raw latency in Cases 2 and 4,
whereas the paper places Hermes ahead of exclusive under high
processing cost. The simulation cannot reproduce the kernel-side costs
that degrade real epoll-exclusive under load: the O(#ports) wait-queue
traversal (the simulated deployment has a single port where production
load balancers serve tens of thousands), wakeup overhead, and the
cache-unfriendliness that kept the round-robin variant out of the
mainline kernel. Stripped of those costs, the model's all-busy path
behaves like an ideal work-conserving central queue, which is a strong
scheduler under uniform saturation. The latency comparison between
Micro-Hermes and exclusive should therefore be read as conservative
towards Micro-Hermes. Case 5 supplies the measured counterweight
within the simulation itself: the same concentration that lets the
exclusive model post low dispatch latency costs it a three-to-four-fold
latency penalty the moment its accumulated connections become active.

Second, Micro-Hermes only matches rather than beats reuseport's
balance in Case 3. The paper's production advantage (a standard
deviation of 20 against 50) arises because real connections have
wildly uneven durations, degrading a stateless hash's balance over
time, whereas Case 3's synthetic connections are identical and never
close, leaving the hash near-optimal by construction. Parity is
accordingly the faithful expectation here, and the qualitative claim
that survives is the one that matters: the LIFO model's balance is an
order of magnitude worse than either alternative's, and only
status-aware dispatch avoids every failure mode observed across the
four cases.

Finally, the paper's CPU overhead profile (0.674% to 2.436% total
across counters, scheduler, syscalls and the eBPF dispatcher) cannot
be meaningfully validated in a simulation whose processing consists of
sleeps; overhead measurement is deferred to Phase 2, where flamegraph
profiling of the real instrumented event loop becomes possible.

Within its stated boundaries, the evaluation supports the central
claims of the Hermes design: the three-stage feedback loop balances
load more evenly than either standard Linux mechanism, detects and
routes around hung workers within a bounded window using only three
atomically-updated metrics, degrades gracefully to reuseport behaviour
when its candidate set thins, and, uniquely among the three mechanisms
tested, remains competitive in every traffic regime.
